# 2026-10-12: the hot path, profiled and cut, on both example installs

Overnight, the PDP and the gateway were profiled under load, and the work behind a check was
cut. Each change was measured locally first, then both example installs were load-tested
before and after:

- #282, #299: the PDP's decision path.
- #296: the gateway.
- #301: `TCP_NODELAY`.
- #303: activity batches.

## How

- **Locally,** on one Mac. CPU profiles came from macOS `sample`.
  - **`pdp_bench`:** the PDP's check path in one process (#282).
  - **PDP alone:** a local `awzy-pdp` with Kafka from `deploy/local`, driven by `pdp_loadtest`.
  - **Whole tool call:** `gateway_bench` (#296) driving a local `awzy-gateway` in front of that
    PDP and a stub MCP upstream.
  - Late in the night other builds loaded the machine, and local numbers from then are noisy.
    They're marked where they appear.
- **In the installs.** `pdp_loadtest` ran from the PDP's image as a pod, with 16 clients for
  180 s and a connection per client, as in the evening runs of
  [2026-10-11](2026-10-11-example-install.md). Each PDP pod's CPU was sampled every 30 s.
  - **AWS:** the example client's install, on 2× `t3.large` (2 burstable vCPUs each).
  - **GCP:** the GCP example's, on 2× `e2-standard-4` (4 vCPUs each).
  - **Autoscaling:** the PDP autoscales from 2 to 4 pods on both.
  - **Profiles:** in-cluster CPU profiles (`AWZY_PROFILING`) run, but don't unwind yet (#298).

## Where a check's CPU went

A local PDP under `pdp_loadtest`, before #282:

| | Share of PDP CPU |
| --- | --- |
| Cedar's evaluation (`is_authorized`) | 25% |
| Turning request entities into Cedar's (its JSON parser) | 18.5% |
| Turning the context into Cedar's (its JSON parser, the schema's type each time) | 15.5% |
| gRPC, HTTP/2, and the server's middleware | about 30% |
| Policy IDs, challenge annotations, and the rest | about 10% |

About 8% of all the PDP's CPU was serde building error messages. Cedar's JSON parser tries
several shapes for each value and formats an error for each one that doesn't fit. #279 tracks
the costs left inside Cedar.

What changed:

- **#282:**
  - Entities are parsed once per bundle and kept by their JSON.
  - A context is built from its values directly and then validated against the schema.
  - Each policy's ID and challenge are worked out once.
- **#299:**
  - A check evaluates only the policies whose scope can match its action. A `read` could match
    13 of the base bundle's 31, and Cedar builds every policy's condition for every request.
  - A request's whole entity set, with Cedar's transitive closure, is kept too.

On one core, `pdp_bench` went from about 103 µs per decision on `main` to 73 µs with #282,
and from about 84 to 44 µs with #299. The second pair was measured on a busier machine.

Over the night, the AWS install went from 2,987 to 4,525 checks/s (+51%), with p99 from 20.2 to
13.9 ms. The GCP install went from 4,137 to 5,814 checks/s (+41%), with p99 from 11.7 to 9.1
ms, inside the 10 ms budget.

- **CPU per check fell by 40% on AWS and a third on GCP.** Throughput rose less,
  because the nodes are the ceiling: on both installs the PDP autoscaler sat at its 4-pod
  maximum and the nodes ran near 100% CPU. The load generator (about 0.7 cores) shares them.
- **What else used CPU at 3,568 checks/s on AWS:** ClickHouse ingesting the decisions, 161m;
  the OTel collector, 169m. Neither is close to a limit.
- **Pass condition** (p99 under 10 ms at 1,500 checks/s): these runs push each install to
  its ceiling, well past 1,500/s. GCP holds p99 under 10 ms even there (9.1 ms at 5,814/s).
  AWS, on burstable vCPUs, is at 13.9 ms at 4,525/s. A run held at 1,500 checks/s, to check AWS
  against the condition as written, is the next one to do.

## A tool call through the gateway, locally

`gateway_bench` with 8 clients for 20 s, through the gateway and PDP to a stub upstream:

| | Before #296 | #296 |
| --- | --- | --- |
| Calls/s | 1,827 | 3,608 |
| p50 | 2.54 ms | 1.43 ms |
| p99 | 28.1 ms | 11.7 ms |
| Gateway CPU per call | 400 µs | 264 µs |

A fifth of the gateway's samples were threads waiting on locks:

- **The PDP connection.** Every check shared one HTTP/2 connection to the PDP.
- **stdout.** Each monitor-mode call that would have been blocked wrote a log line.

#296 opens a few PDP connections and moves that line to debug. It also remembers verified
tokens until they expire. Its HS256 test tokens are cheap to check, so in an install, where
the IdP signs with RS256 or ES256, the saving is larger.

#301 sets `TCP_NODELAY` on every served connection and on `awzy_http`'s clients. Without it, a
small HTTP/2 answer can wait on Nagle's algorithm for the peer's delayed ACK. In one local run
the gateway path went from 2,087 to 5,996 calls/s and p99 from 37.5 ms to 6.2 ms. A repeat on
the swamped machine didn't show it, so the installs' runs are the measure. With #301 alone
between the two releases, AWS went from 3,794 to 4,525 checks/s and GCP from 4,644 to 5,814,
and p99 fell on both. Each closed-loop client waits less for each answer and so sends more.
