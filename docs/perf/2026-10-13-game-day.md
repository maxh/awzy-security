# 2026-10-13: game day, each dependency taken away (#353)

The PDP and gateway had been load-tested in the example installs, not failure-tested. This run
takes one dependency away at a time, under load, on both example installs. For each it records
what running PDPs decide, whether a new PDP becomes ready, whether decision records are lost,
which alerts would fire, and how long recovery takes. How to run one, and what we learned about
running them, is in [game-days.md](game-days.md).

## Dependencies

What each part of the hot path needs, read from the code on `70aefe4`, and what it does when the
dependency is gone. "Starting" is a pod that comes up while the dependency is away.

| Component | Needs | Running, the dependency gone | Starting, the dependency gone |
| --- | --- | --- | --- |
| Enforcement points (gateway, SDKs) | The PDP, on every check | After a 500 ms connect timeout or a 2 s request timeout, the signed outage fallback (ADR 0030) | Starts; fallback settings come from awzy-policy, containments from awzy-challenge |
| PDP | awzy-policy: the bundle and modes, polled every 10 s | Keeps what it has, no limit | From a running PDP, verified (ADR 0119) |
| | awzy-context: the principals snapshot (long poll) | Keeps what it has, no limit | From a running PDP |
| | awzy-context: resources, on a cache miss (30 s TTL, 300 s while the change feed is heard; 5 s for one awzy-context doesn't know) | A cached entry serves up to its tier's limit (public and internal 60 min, confidential 15, crown jewels and unknown 5); a miss asks a running PDP | Misses ask a running PDP |
| | awzy-challenge: the containment feed (a heartbeat every 0.5 s) | After 2 s without one, asks awzy-challenge directly (250 ms timeout); then the last list for up to 5 minutes; then checks fail | From a running PDP, with the peer's age |
| | Kafka: the decision and plan logs | Records queue in a 20,000-record buffer per PDP; a batch that fails 5 times (about 3 s of backoff) is dropped and counted | **Exits**: it connects and creates its topics before serving |
| awzy-policy, awzy-context, awzy-challenge | Postgres | Requests that touch the database wait or fail | Exit: they connect before serving |
| awzy-policy | The install's KMS key | Publishing fails | Exits: it connects to the key at start |
| ClickHouse | Kafka (the decision and event tables read topics) | Waits; records stay in Kafka for its retention | |

Once running, the PDP's only hard dependency is Kafka, and only for the audit trail. At start it
needs Kafka and one running PDP (or every source).

## Setup

- **Installs:** both example installs, `small` profile.
  - AWS: 2× `t3.large`, Aurora Serverless with one instance, Amazon MSK with 2 brokers.
  - GCP: 2× `e2-standard-4`, zonal Cloud SQL, in-cluster Kafka (Strimzi, 1 broker).
- **Releases:** `516e887` and `2a3bc85` for most runs, and `6e030ac` (#397) for the node drains.
- **Load:** `pdp_loadtest` in open loop at 200 checks/s over 8 connections, with a line a second
  (#393). The 2 s per-check limit matches the gateway's.
- **Harness:** [`tools/gameday/gameday.sh`](../../tools/gameday/gameday.sh):
  - 60 s of load, then the dependency is taken away.
  - 30 s later one PDP pod is deleted, so its replacement has to start without the dependency.
  - The dependency comes back, then 120 s more of load.
  - PDP metrics are sampled every 5 s.
  - Afterwards, decision records are counted in ClickHouse. Each check writes one, plus 200
    warm-up checks, so the count shows any loss.
- **Alerts:** neither install evaluates the alert rules. The GCP install doesn't scrape awzy's
  metrics at all (see below), so "would fire" means the rule's expression held on the sampled
  metrics.

## Results

| Scenario | Install | Away | Checks | Failed | Slow | New PDP ready | Records lost |

| awzy-policy at 0 | GCP | 180 s | 78,000 | 0 | none | 6 s, from a peer | 0 |
| awzy-context at 0 | GCP | 420 s | 126,000 | 23,095 (18%) | every check ~1 s | 6 s | 0 |
| awzy-context at 0 | AWS | 180 s | 78,000 | 6,079 (8%) | every check ~1 s | 9 s | 0 |
| awzy-challenge at 0 | GCP | 420 s | 126,000 | 18,954 (15%) | none | 8 s | 0 |
| Aurora writer rebooted | AWS | about 45 s | 78,000 | 0 | 22 s at ~1 s | not sampled | 0 |
| Cloud SQL restarted | GCP | 19 s | 90,000 | 0 | 7 s at ~1 s | at once | 0 |
| One MSK broker rebooted | AWS | 4 min | 138,000 | 0 | none | 21 s | 0 |
| The only Kafka broker | GCP | about 9.5 min | 90,000 | 0 | none | **crash-looped**, ready 2 min after Kafka | **57,352 (64%)** |
| One node drained | GCP | 15 min | 102,000 | 0 | 3 s | 13 s | 0 |
| One node drained | AWS | 16 min | not measured | | | **not until the node returned** | |

### awzy-policy

Nothing changed for checks. The policy sync age reached 190 s, so `AwzyPdpPolicySyncStale` would
have fired. ADR 0119's case held: a PDP starting while awzy-policy is down takes the bundle from a
peer and is ready in seconds.

### awzy-context

- **Every check took about 1 s for the whole outage**, on both clouds. Neither GKE nor EKS
  refuses a connection to a Service with no endpoints: the connection hangs. Each check whose
  cache entry had expired fetched again and waited out the 1 s timeout before falling back to the
  stale entry. **Fixed by #397:** after a failed fetch, the PDP skips awzy-context for a second.
  An outage now costs one timeout a second, not one per check.
- **Some checks went past 2 s** (the gateway's limit), mostly on PDPs the autoscaler added
  during the outage: the 1 s fetch timeout, then the peer ask (up to 5 peers at 250 ms each).
  #397 removes the first part during the pause.
- **After 5 minutes every check failed `Unavailable`** until awzy-context returned, then
  recovered within 5 s. The load used only resources awzy-context doesn't know, which get the
  shortest stale limit (5 minutes, ADR 0119). In a real install only crown-jewel and unknown
  resources would fail this soon; public and internal ones last 60 minutes.
- The principals and resource feed ages reached 444 s, so `AwzyPdpPrincipalsSyncStale`,
  `AwzyPdpResourceFeedStale`, `AwzyPdpServingStaleResources`, and then `AwzyPdpCheckErrors` would
  have fired.

### awzy-challenge

As ADR 0119 designed it. Checks were unaffected for 5½ minutes on the last containment list,
then every check failed `Unavailable` until awzy-challenge returned, and recovered within 5 s.
`AwzyPdpContainmentFeedStale` would have fired after a minute. So an awzy-challenge outage
longer than 5 minutes is a total outage of checks, and enforcement points fall back. That's the
trade-off the ADR made (a stale containment list mustn't be trusted for long); this run puts a
time on it.

### Postgres

A short database outage costs a few seconds of slow checks. The cause is the same as the
awzy-context outage: awzy-context stays up and its queries wait. Nothing failed, and new PDPs
were ready. On AWS there's no Aurora replica, so this was a reboot of the only writer, not a
failover.

### Kafka

- **One broker of two (MSK):** no effect at all.
- **Every broker:**
  - Checks never failed. But the PDPs kept only what fit in their buffers: about 20,000 records
    each, or 100 s at this rate. The rest was dropped (`awzy_pdp_decisions_dropped_total{reason="buffer_full"}`
    reached 54,310 on one pod), and 64% of the run's decision records never reached ClickHouse.
    The audit trail of any Kafka outage longer than about a minute and a half is lost, which is
    #348's open question (save records to disk before dropping them) with a number on it.
  - **A PDP can't start without Kafka.** The replacement crash-looped 7 times and became ready
    about 2 minutes after the broker did, held back by the crash-loop backoff. ADR 0119 removed
    the PDP's start-up dependence on Postgres and the control plane, but not this one. During a
    Kafka outage the install can't replace a PDP, scale out, or survive a node loss.
- The outage lasted about 9½ minutes rather than the planned 4: Strimzi took 5 minutes after its
  operator restarted to recreate the broker.

### A node

- **GCP:** the drain respected the PodDisruptionBudgets and every evicted pod found room on the
  other node. No check failed. Once the second PDP was deleted, its replacement stayed `Pending`
  until the node returned, so the install ran on one PDP.
- **AWS:** the cluster has no room for a node's pods. Both nodes have 85–88% of their CPU
  requested, and there's no cluster autoscaler.
  - The PDP, awzy-context, awzy-challenge, the gateway, and awzy-intake ran one pod each for all
    16 minutes, with the evicted pods `Pending` ("Insufficient cpu").
  - In an earlier run, both PDPs had been placed on the same node. Pods are spread across nodes
    with `whenUnsatisfiable: ScheduleAnyway`, a preference, so losing that node would have taken
    every PDP: a cold start.
  - The drain also evicted the load pod, so there's no check timeline for this run.
  - This is #349 measured: the `small` profile on AWS can't absorb losing a node.

## Not run

- **The cold start** (every PDP restarted while awzy-context is away).
- **awzy-context again with #397**, to measure the fix in the install.
- **The gateway's own fallback:** a PDP outage as a tool call through the gateway sees it.
- **An Aurora failover to a replica**, since the AWS install has none.
- **One node lost abruptly** rather than drained.

## Follow-ups

1. **The PDP starts without Kafka:** serve checks, buffer records, and connect in the
   background, as ADR 0119 does for the other sources.
2. **Decision records survive a Kafka outage longer than the buffer** (#348): to disk, or a
   documented promise about the audit trail.
3. **The `small` profile survives a node** (#349): headroom on AWS, and PDPs spread across nodes
   as a requirement (`DoNotSchedule`) when there are enough nodes.
4. **The GCP example install scrapes awzy's metrics and evaluates the alert rules.** Today GMP's
   rule evaluator and Alertmanager run zero replicas and nothing scrapes awzy, so an outage there
   pages no one.
5. **Run the rest** of the list above, and make the game day part of a release check.
